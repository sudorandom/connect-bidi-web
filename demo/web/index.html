connect-bidi-web

Full bidirectional streaming for ConnectRPC in the browser — over WebSockets and WebTransport.

Connect's HTTP protocol can't carry full-duplex streams in the browser. connect-bidi-web adds pluggable transports that can, so your existing Connect services gain real bidi streaming without switching protocols or making bespoke WebSocket solutions.

View on GitHub Try the live demo

Ships as Go packages (github.com/sudorandom/connect-bidi-web) and npm packages under @sudorandom/connect-bidi-web.

What it is

ConnectRPC's Connect protocol runs over plain HTTP, which makes it simple, cacheable, and proxy-friendly — but browsers won't let fetch stream a request body while also reading the response, so a browser can't drive a truly bidirectional RPC over HTTP alone.

connect-bidi-web adds transports, built on connect-go v2's new Transport API and on connect-es, that carry the same Connect envelope protocol over two full-duplex transports instead:

WebSocket

One WebSocket connection per RPC. Works in every evergreen browser today, including through proxies and edge platforms like Cloudflare Workers.

WebTransport

One HTTP/3 session per client, one QUIC stream per RPC. Multiple concurrent streams share a single session with no head-of-line blocking between them.

Composite transport

Keeps unary RPCs on plain HTTP for caching, observability, and proxy support, and routes only streaming RPCs over the bidi transport — you don't have to choose one transport for everything.

In the browser — connect-es

Client transports for the browser, used by the live demo below with the same ElizaService.

npm npm install @sudorandom/connect-bidi-web
TypeScript Browser client — WebSocket 
import { createClient } from "@connectrpc/connect";
import { createConnectTransport } from "@connectrpc/connect-web";
import {
  createCompositeTransport,
  createConnectWebSocketTransport,
} from "@sudorandom/connect-bidi-web";
import { ElizaService } from "./gen/connectbidi/eliza/v1/eliza_pb.js";

const transport = createCompositeTransport(
  // Unary RPCs: plain Connect over HTTP.
  createConnectTransport({ baseUrl: "https://localhost:4433" }),
  // Streaming RPCs: one WebSocket connection per RPC.
  createConnectWebSocketTransport({
    baseUrl: "https://localhost:4433",
  }),
);

const client = createClient(ElizaService, transport);

for await (const res of client.converse(requests())) {
  console.log(res.sentence); // full bidi streaming!
}
TypeScript Browser client — WebTransport 
import { createConnectWebTransportTransport } from "@sudorandom/connect-bidi-web";

// One HTTP/3 session, reused for every streaming RPC.
const session = new WebTransport("https://localhost:4433/webtransport");

const transport = createCompositeTransport(
  createConnectTransport({ baseUrl: "https://localhost:4433" }),
  createConnectWebTransportTransport({
    baseUrl: "https://localhost:4433",
    session,
  }),
);

On the backend — connect-go

Server handlers for both transports, plus a Go client transport, built on connect-go v2's Transport API.

Go go get github.com/sudorandom/connect-bidi-web
Go Server 
server := connect.NewServer()
elizav1connect.RegisterElizaServiceHandler(server, elizaServer{})

// One connection per RPC, over a plain net/http handler.
http.Handle("/websocket", connectwebsocket.NewHandler(server))

// WebTransport: one HTTP/3 session, one stream per RPC.
webtransportHandler := connectwebtransport.NewHandler(server)
// ...on every accepted session:
webtransportHandler.HandleSession(ctx, session)
Go Client 
transport := connectwebsocket.NewTransport("wss://api.example.com/websocket")
client := elizav1connect.NewElizaServiceClient(connect.NewClient(transport))

stream := client.Converse(ctx)
// stream.Send(...), stream.Receive(), full duplex.

Run it yourself

The whole demo — site, Go server, and Cloudflare Workers variant — lives in the repo.

Shell Local demo 
git clone https://github.com/sudorandom/connect-bidi-web
cd connect-bidi-web
mise install       # dev tools: go, node, buf, just, mkcert, wrangler, ...

just demo          # Go server: https://localhost:4433
                   #   Connect HTTP + WebSocket + WebTransport
just demo-worker   # Cloudflare workerd: http://localhost:8787
                   #   Connect HTTP + WebSocket (no WebTransport on Workers)

The first run of just demo creates a locally-trusted TLS certificate with mkcert. Browsers hold WebTransport certificates to stricter rules than HTTPS, so local WebTransport needs one tweak on top:

  • Chrome — enable chrome://flags/#webtransport-developer-mode. By default, WebTransport ignores locally-installed roots like mkcert's.
  • Firefox — in about:config, set network.http.http3.disable_when_third_party_roots_found to false.

To point the live demo at your local server, use the server box above or a ?server= query parameter.

Support matrix

Transport Browsers Infrastructure Connection model
WebSocket All evergreen browsers Nearly universal Passes through proxies, load balancers, and edge platforms (Cloudflare Workers, Vercel, …) One connection per RPC.
WebTransport Chrome 97+, Edge 98+, Firefox 114+, Safari 26.4+ (Baseline across major browsers since March 2026) Patchy Needs an end-to-end HTTP/3 (UDP) path; most load balancers, gateways, and edge platforms can't carry it yet One HTTP/3 session, one QUIC stream per RPC.

The live demo above feature-detects WebTransport in the browser ("WebTransport" in globalThis) and asks the selected server whether it terminates HTTP/3, disabling that dropdown option wherever either end doesn't support it.

Why “not supported here”?

Case in point: the hosted version of this very site runs on Cloudflare Workers, which don't yet support WebTransport — Workers expose no QUIC or UDP path to your code. Served from the Worker, the live demo above offers WebSocket only; served from the Go demo server, both transports light up.

The endpoints are ready. WebTransport is Baseline in evergreen browsers, most HTTP/3 stacks implement it, and server-side support is mature in Go (quic-go/webtransport-go, which this project builds on), Rust (wtransport), and others.

The gap is everything in between. WebTransport rides HTTP/3 over QUIC — UDP, not TCP — and needs an end-to-end HTTP/3 path:

  • Load balancers and CDNs often terminate HTTP/3 at the edge for ordinary requests, but don't accept Extended CONNECT sessions or forward them upstream.
  • API gateways and reverse proxies commonly speak HTTP/1.1 or HTTP/2 to the backend, a hop the WebTransport session can't cross.
  • Serverless and edge platforms (Cloudflare Workers, Vercel, …) expose no UDP or QUIC path to your code at all.
  • Firewalls and restrictive networks silently drop UDP on port 443. Ordinary HTTP falls back to TCP; a WebTransport connection just fails.
  • Browsers themselves hold WebTransport to stricter certificate rules than HTTPS: Firefox disables HTTP/3 entirely for any certificate chaining to a third-party root (network.http.http3.disable_when_third_party_roots_found) — common under corporate proxies and antivirus — and Chrome only accepts WebTransport certificates from well-known roots unless chrome://flags/#webtransport-developer-mode is enabled. Locally-installed CAs like mkcert's hit both rules.

That's exactly why these transports are pluggable and composite: unary RPCs stay on plain HTTP everywhere, streaming RPCs use WebTransport when the whole path supports it and fall back to WebSocket — which traverses all of the above — when it doesn't. A greyed-out option means either this browser lacks the WebTransport API, or the selected server reported (via /capabilities.json) that it can't terminate HTTP/3.
