connect-bidi-web

A testbed for ConnectRPC over WebSockets.

Connect's HTTP protocol can't carry full-duplex streams in the browser. A WebSocket can. This is where that protocol gets designed: competing drafts, each fully implemented in Go and TypeScript, then benchmarked against each other.

What this is

An experiment in progress, not a finished product. Four wire protocol drafts for carrying Connect RPCs over a WebSocket, each implemented end to end in Go and TypeScript and served side by side, so the designs can be measured rather than argued about.

They are real transports for connect-go and connect-es, built on connect-go v2's Transport API and the connect-es transport interface, so they drop in where the HTTP transport would. WebTransport is here too, as the comparison that shows what the WebSocket drafts are working around.

WebSocket over HTTP/1.1

The classic Upgrade handshake, on its own TCP connection. One connection carries any number of concurrent RPCs; a stream ID on every frame tells responses which caller they belong to. This is the one that works nearly everywhere: it goes through the proxies, load balancers, gateways, and serverless platforms that already carry HTTP.

MDN · RFC 6455

WebSocket over HTTP/2

The same frames, bootstrapped with extended CONNECT instead. Each WebSocket becomes one stream on a connection the browser already has, so it costs no extra TCP or TLS handshake.

Both ends must opt in. Go gates it behind GODEBUG=http2xconnect=1. Browsers pick this bootstrap on their own when the server advertises it; JavaScript cannot force or observe the choice. The Go library that handles the HTTP/1.1 path cannot accept over HTTP/2, so the framing and the permessage-deflate extension are implemented directly here.

RFC 8441

WebTransport

One HTTP/3 session per client, one QUIC stream per RPC. The streams are independently flow-controlled, so there is no head-of-line blocking between them and the protocol needs no stream IDs at all.

You probably can't rely on this 'just working'. It needs HTTP/3 over UDP all the way to your handler, which rules out most L7 load balancers, gateways, and serverless platforms. See where each transport works.

MDN · W3C spec · WebTransport over HTTP/3

Composite and fallback

Two ways to combine the above. A composite transport keeps unary RPCs on plain HTTP — for caching, observability, and proxy support — and sends only streaming RPCs over the bidi transport. A fallback transport tries a ladder of them, best first, and remembers which rung worked.

In Go the ladder is WebTransport, then WebSocket over HTTP/2, then HTTP/1.1. In the browser it collapses to WebTransport then WebSocket: the browser chooses the WebSocket bootstrap itself.

How the protocol works

One invariant: the Connect protocol's semantics stay intact. How the framing around them is spent is what the drafts disagree about.

The same codecs, the same error codes and details, the same trailers. What cannot survive the upgrade is what Connect borrows from HTTP — per-request headers, a way to tell concurrent RPCs apart, half-close, and RST_STREAM. The frames below replace them, and the drafts disagree about how many are needed: drafts 1 and 5 give each RPC its own socket, so they need no stream ID and no reset; drafts 3 and 4 multiplex, and pay for both.

The four frame kinds the drafts spend their bytes on

Headers frame

Opens every stream, carrying what would have been the HTTP headers as JSON: the :path, the content type, the deadline.

Stream ID

A 4-byte prefix on every frame, so many RPCs share one connection. Clients count up from 1 and never reuse an ID — the job HTTP/2 stream IDs do for Connect over HTTP.

End-stream frame

Ends a response with Connect's own EndStreamResponse JSON. Requests reuse it empty as a half-close: done sending, still listening.

Reset frame

Cancels one stream without killing the others, like HTTP/2's RST_STREAM. The server cancels that handler's context.

Five wire formats

Five wire-incompatible drafts coexist, all selectable in the demo above. Draft 1 is the proposal: one WebSocket per streaming RPC, unary left on HTTP. Drafts 3 and 4 multiplex everything onto one connection and get a path each (/websocket-draft3, /websocket-draft4), disagreeing only about where framing and compression belong. Draft 5 keeps draft 1's connection model and removes the envelope. Draft 7 is the written specification: draft 5's model with one marker byte put back, and every loose end — codec selection, deadlines, metadata rules, origin checks, size limits — pinned down.

Draft 1 One socket per RPC + Connect's own envelope
Flags Meaning
0x00 data — one RPC message
0x02 end-stream — empty on requests (half-close); Connect EndStreamResponse JSON on responses
0x06 headers — opens each direction; JSON metadata. No :path: the URL already named the procedure.

That is the standard 5-byte Connect envelope, unchanged, one per binary WebSocket message; the length restates the message boundary, which is what leaves the envelope Connect's own byte for byte. There is no stream ID and no reset flag, because one socket carries one RPC — cancelling is closing it — and the compressed-data flag (0x01) goes unused, since compression is permessage-deflate with no_context_takeover. The headers envelope opens each direction, the server's too, because a browser can neither set headers on the upgrade nor read them off the response. Streaming RPCs dial the procedure's own URL; unary never upgrades.

Draft 3 A packed 5-byte head + compression as a protocol option
Descriptor Meaning
0x00 data — one RPC message
0x01 headers — opens every stream; JSON metadata with :path, content-type, …
0x02 end-stream — empty on requests (half-close); EndStreamResponse JSON on responses
0x03 reset — empty; aborts one stream
0x80 compressed bit (bit 7) — ORed onto any type: the payload is one raw DEFLATE stream

The descriptor byte packs the frame type into bits 0–6 and a compressed flag into bit 7, so 0x80 is compressed data. Compression is negotiated once per connection, by WebSocket subprotocol: the client offers connect.bidi.d3.deflate, the server echoes its pick. Each frame deflates independently, and senders skip payloads under 512 bytes. Subprotocols travel on both bootstraps, so this works over HTTP/1.1 and HTTP/2 alike. Served on /websocket-draft3.

Draft 4 An ASCII frame head you can read on the wire
Flags Meaning
0 data — one RPC message
1 headers — opens every stream; JSON metadata with :path, content-type, …
2 end-stream — empty on requests (half-close); EndStreamResponse JSON on responses
3 reset — empty; aborts one stream

Both head fields are plain decimal ASCII, so a frame reads as text. Parsers split on the first two | only, so a payload containing | needs no escaping. Frames whose payload is UTF‑8 go out as text WebSocket messages, which is what makes devtools show them as text. The flags field holds the frame type in its low 3 bits; receivers ignore the five bits above it, so a later revision can add a flag without breaking anyone. Compression is permessage-deflate, negotiated in the handshake and working over both bootstraps. Served on /websocket-draft4.

Draft 5 No frame at all — the handshake is the request
WebSocket opcode Meaning
text, empty separator — and only this: the one message shape the protocol reserves
text headers (first in each direction), the EndStreamResponse (last from the server), or an RPC message whose payload is non-empty UTF‑8
binary an RPC message that is empty or not UTF‑8. Position tells data from metadata.

There is no frame diagram because there is no frame: a data message is exactly the bytes the codec produced. The only framing is the opcode RFC 6455 already sends, with one shape reserved — an empty text message is the separator, so empty payloads travel as binary and a service whose messages are sometimes empty cannot half-close by accident. The first message is metadata in both directions, and mandatory, for the same reason draft 1's is. The URL is the procedure, so draft 5 has no path of its own; unary never upgrades; and permessage-deflate is the only compression, with no envelope to carry a compressed bit.

Draft 7 The specification: one marker byte, and the frame type names the encoding
Marker Meaning
M leading metadata — first in each direction, a JSON object of names to string arrays, {} when empty
B body — one RPC message; a text frame under JSON, a binary one under Protobuf
C client end-of-stream — bare, or carrying the final body
S server end-of-stream — Connect's EndStreamResponse JSON

Draft 7 is the Connect-over-WebSocket Protocol specification, and it settles what the drafts before it argued about. It keeps draft 5's connection model — one RPC per WebSocket, the handshake naming the procedure — and puts back exactly one byte of framing: a printable marker, so a message says what it is instead of relying on its position. The codec is chosen by the subprotocol (connectrpc.1+json, connectrpc.1+proto, or the base connectrpc.1 for JSON), so the frame type can name the encoding; the deadline rides on the handshake URI as connect-timeout-ms, because a browser can set nothing else; and the metadata object is flat, with a rule for every key. Compression is permessage-deflate with no_context_takeover required in both directions. The specification calls for an HTTP/1.1 handshake only; this implementation serves RFC 8441 extended CONNECT as well, because a browser that has seen the setting on an HTTP/2 connection uses it with no fallback. On this site it is served under /websocket-draft7, the path prefix the specification provides for.

The trade-offs: draft 3 owns its compression, so it works the same on both bootstraps and in both directions no matter which client connects. Draft 4 hands that to permessage-deflate — which works in a browser, but leaves the upload direction up to the client — in exchange for a wire you can read in the browser's Network tab, and pays with a frame head that grows as a connection ages. Draft 5 spends nothing per message and pays per connection instead: a handshake for every streaming RPC, which the benchmarks show it earns back after roughly 75 messages. Draft 7 spends one byte more than draft 5 on every message and buys a protocol that can say what a message is. All of them carry identical Connect semantics; the benchmarks show what each costs.

WebTransport needs almost none of this. QUIC already gives every RPC its own independently flow-controlled stream, with native half-close and cancellation, so there the protocol is exactly Connect's own envelopes plus a headers frame, and nothing else. The stream ID and reset frame exist only where the transport can't do that job itself — which is also the observation draft 5 acts on, by giving every RPC a WebSocket of its own.

Sharing one TCP connection costs head-of-line blocking: a huge message, or a stalled consumer, delays everything queued behind it, and there is no per-stream flow control. Both clients can dial a dedicated connection per streaming RPC instead (connectionPerStream in TypeScript, WithConnectionPerStream() in Go). It is a client choice only; the protocol is identical either way.

Reading the numbers

Highlights worth noticing: drafts 1 and 3 each spend 5 bytes of protocol per message and draft 4 spends 4 to 15, while draft 5 spends none — and still comes out cheapest over a 100-roundtrip stream, handshake included. Draft 1 is draft 5 plus its envelope, and the tables price that at exactly those 5 bytes a message and nothing else. Draft 3 is the only variant here that compresses what the client sends, taking the compressible 16 KiB upload down to about 140 bytes. On incompressible text every deflate row lands at the same ~12.4 KB, which is what honest compression looks like.

Two rows are easy to misread. Draft 5's unary rows measure a different transport: it never upgrades for unary, so those numbers are an ordinary Connect POST, its identity/deflate label does not apply, and its 16 KiB response comes back at ~294 B because Connect's own gzip covers it where the WebSocket drafts' uncompressed rows carry the full payload. And on Bidi ×100 every draft's deflate rows match its identity rows — those messages are far too small to compress — except drafts 1 and 5, which each come out 102 bytes larger: all that arrives is the permessage-deflate negotiation in the handshake, which a socket-per-RPC draft pays on every RPC where the multiplexing drafts pay it once per connection.

Bidi 16 KiB is the workload that shows compression doing its job on a stream rather than on a unary call, and it exists because its absence was misleading: with only the unary rows to go on, draft 5's deflate looked like it did nothing at all. It compresses 65 KB down to about 1.2 KB, a little behind drafts 3 and 4 because a per-RPC connection cannot amortize the handshake across calls.

That upload column deserves a caveat, because it is measured with a Node client. Under permessage-deflate, compressing an outgoing message is each endpoint's own choice — RSV1 is set per message — and Node's built‑in WebSocket declines: it negotiates the extension, inflates what it receives, then uploads everything in full. Browsers do not behave that way. The same 16 KiB upload leaves Chrome at 106 bytes and Firefox at 168. So drafts 1 and 4 compress both directions in a browser; what draft 3 buys is not needing to care which client you get.

Conclusions

What five coexisting drafts and a byte-counting benchmark suite settled.

Don't duplicate the layer below

A WebSocket message already carries its own length, and Connect's envelope states it again inside the frame. Draft 1 keeps the envelope anyway, so a payload stays byte-for-byte Connect's; the benchmarks price that redundancy at exactly 5 bytes per message. Draft 5 finishes the thought and drops the frame entirely, which also removes a whole class of error — two sources of truth for one length can disagree.

A feature below your abstraction can vanish silently

Draft 4 leaves compression to the WebSocket layer. Swapping that layer for the HTTP/2 one dropped it entirely — the same 16 KiB payload went out at 16.8 KiB instead of 327 B, with no error and no failing test. Draft 3 owns its compression, above that boundary, and was never affected. We since implemented the extension on the HTTP/2 path too; the bug was the lesson.

Optimize for the client that reads it

Browsers are the main WebSocket client, and their Network tab is where this traffic gets read. Drafts 1 and 3 show up there as hex. Draft 4's frames read as text.

Text framing is cheap; the codec is not

Draft 4 with protobuf costs 3 bytes more than draft 3 on a 16 KiB message. Switching to JSON, so the payloads are readable too, is what costs: about 2× the time.

Fallback needs three contracts

Transports must report connection failures differently from RPC failures. Every dial needs a timeout. A retried stream needs a replayable request iterator.

Recommendation

Draft 7, the specification, is where the drafts converged: draft 5's connection model — the cheapest on the wire past about 75 messages, at the price of a connection per RPC — with one marker byte so that a message says what it is, and every rule written down. Draft 4 when you want to read the traffic in devtools. Draft 3 when bytes matter across many short, concurrent streams, or when you need compression over HTTP/2. WebTransport when you control the UDP path.

Why is WebTransport not shown in the demo?

Because the server you are talking to right now can't speak it. The hosted version of this site runs on Cloudflare Workers, which don't yet support WebTransport: Workers expose no QUIC or UDP path to your code. Run the Go demo server locally and both transports work.

Both ends are fine on their own. Every major browser ships WebTransport now, and server-side support is mature in Go (quic-go/webtransport-go, which this project builds on), Rust (wtransport), and elsewhere.

What usually breaks is the path between them. WebTransport runs on HTTP/3 over QUIC, so UDP has to reach your handler and every hop has to pass Extended CONNECT. Load balancers and CDNs usually terminate HTTP/3 at the edge and talk HTTP/1.1 or HTTP/2 upstream, which the session can't cross. Serverless platforms tend not to offer UDP at all. Some networks drop UDP on port 443, where ordinary HTTP would fall back to TCP but WebTransport just fails.

Browsers also apply stricter certificate rules to WebTransport than to HTTPS. Firefox disables HTTP/3 when it sees a certificate chaining to a third-party root, which is common under corporate proxies and antivirus, and Chrome only accepts WebTransport certificates from well-known roots unless developer mode is on. A locally-installed CA like mkcert's trips both.

Hence the composite transport: unary RPCs stay on plain HTTP, streaming RPCs use WebTransport where the path allows it and WebSocket where it doesn't.
