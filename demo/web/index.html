connect-bidi-web

Full bidirectional streaming for connect-go and connect-es, over WebSockets and WebTransport.

Connect's HTTP protocol can't carry full-duplex streams in the browser. These transports can, and they plug into the server and client you already have.

github.com/sudorandom/connect-bidi-web on pkg.go.dev, @sudorandom/connect-bidi-web on npm.

What it is

Transports for connect-go and connect-es that carry the Connect envelope protocol over a full-duplex connection instead of HTTP. They use connect-go v2's Transport API and the connect-es transport interface, so they go where the HTTP transport would.

WebSocket

One shared connection, any number of concurrent RPCs. Every frame carries a stream ID so responses find their caller. Runs over TCP, so it goes through the proxies, load balancers, gateways, and serverless platforms that already carry your HTTP traffic.

MDN · RFC 6455

WebTransport

One HTTP/3 session per client, one QUIC stream per RPC. Multiple concurrent streams share a single session with no head-of-line blocking between them.

You probably can't rely on this 'just working'. WebTransport needs HTTP/3 over UDP all the way to your handler, which rules out most L7 load balancers, gateways, and serverless platforms. Use WebSocket unless you control the whole path and have tested it. See where each transport works.

MDN · W3C spec · WebTransport over HTTP/3

Composite transport

Keeps unary RPCs on plain HTTP for caching, observability, and proxy support, and routes only streaming RPCs over the bidi transport.

In the browser: connect-es

Client transports for the browser, used by the live demo below with the same ElizaService.

npm npm install @sudorandom/connect-bidi-web
API reference Package on npm ↗
TypeScript Browser client 
import { createClient } from "@connectrpc/connect";
import { createConnectTransport } from "@connectrpc/connect-web";
import {
  createCompositeTransport,
  createConnectWebSocketDraft1Transport,
} from "@sudorandom/connect-bidi-web";
import { ElizaService } from "./gen/connectbidi/eliza/v1/eliza_pb.js";

const transport = createCompositeTransport(
  // Unary RPCs: plain Connect over HTTP.
  createConnectTransport({ baseUrl: "https://localhost:4433" }),
  // Streaming RPCs: multiplexed onto one shared WebSocket connection.
  // connectionPerStream: true dials a connection per RPC instead,
  // trading a handshake for freedom from head-of-line blocking.
  createConnectWebSocketDraft1Transport({
    baseUrl: "https://localhost:4433",
  }),
);

const client = createClient(ElizaService, transport);

for await (const res of client.converse(requests())) {
  console.log(res.sentence); // full bidi streaming!
}

How the protocol works

One rule: stay as close to the Connect protocol as possible, and add only what a raw socket cannot provide itself.

On the wire, a streaming Connect RPC is a sequence of messages plus one EndStreamResponse JSON at the end. connect-bidi-web keeps the Connect semantics everywhere: the same codecs, the same error codes and details, the same trailers.

What it can't keep is everything Connect quietly inherits from HTTP. Once a WebSocket finishes its upgrade, HTTP leaves the room: there are no more per-request headers, no way to tell concurrent RPCs apart, no half-close, and no RST_STREAM to cancel one call without killing the rest. Each of those gaps becomes one small, explicit piece of protocol:

Headers frame

A dedicated frame type opens every stream, carrying what would have been the HTTP headers as JSON metadata: the :path of the procedure, the content type (which can legitimately differ per RPC), deadlines.

Stream ID

Every WebSocket frame is prefixed with a 4-byte stream ID so many RPCs can share one connection. The receiver uses it to match each message to the appropriate caller. Clients assign IDs starting at 1 and never reuse them, exactly the job HTTP/2 stream IDs do for Connect over HTTP.

End-stream frame

Straight from Connect: the response stream ends with the standard EndStreamResponse JSON. Requests reuse it with an empty payload as an explicit half-close (“done sending, still listening”), since neither the stream nor the WebSocket has one of its own.

Reset frame

Cancellation. Closing a shared connection would kill every RPC on it, and a client that already half-closed has no other frame left to send. So, like HTTP/2's RST_STREAM, a reset aborts exactly one stream and the server cancels that handler's context.

Three drafts, side by side

The WebSocket wire protocol exists in three deliberately coexisting, wire-incompatible drafts, served on different paths (/websocket-draft1, /websocket-draft2, /websocket-draft3, /websocket-draft4) and all selectable in the live demo above, so their designs can be measured against each other. They differ in one idea: where the framing and compression jobs live — in the protocol, in the WebSocket layer, or negotiated between the two.

Draft 1 Stream ID + a standard Connect envelope 
┌───────────┐┌──────┐┌────────────┐┌────────────────┐
│ stream ID ││ flag ││ length     ││ payload …      │
│ (4 bytes) ││ (1)  ││ (4 bytes)  ││                │
└───────────┘└──────┘└────────────┘└────────────────┘
             └──── a standard Connect envelope ─────┘
Flag Frame
0x00 data — one uncompressed RPC message
0x01 compressed data — one message, compressed with the negotiated algorithm
0x02 end-stream — empty on requests (half-close); EndStreamResponse JSON on responses
0x06 headers — opens every stream; JSON metadata with :path, content-type, …
0x07 reset — empty; aborts one stream

Everything after the stream ID is byte-for-byte the Connect protocol's envelope: a flag, a 4-byte payload length, and the payload. Flags are complete byte values, not bitmasks; 0x06 and 0x07 are transport-specific additions, and 0x08 and up are reserved. Compression is Connect's per-message kind, negotiated inside the headers frame's metadata: the client lists the algorithms it accepts in connect-accept-encoding (gzip by default), the server picks one and names it in connect-content-encoding on its response headers frame, and every compressed message is flagged 0x01. Requests work symmetrically when the client configures a send compressor. Headers and end-stream JSON are never compressed. Served on /websocket-draft1.

Draft 2 Stream ID + frame type; the WebSocket does the rest 
┌───────────┐┌──────┐┌────────────────────┐
│ stream ID ││ type ││ payload …          │
│ (4 bytes) ││ (1)  ││ (rest of message)  │
└───────────┘└──────┘└────────────────────┘
Type Frame
0x00 data — one RPC message, always uncompressed
0x01 headers — opens every stream; JSON metadata with :path, content-type, …
0x02 end-stream — empty on requests (half-close); EndStreamResponse JSON on responses
0x03 reset — empty; aborts one stream

No payload length and no compressed-data type: the WebSocket already does both jobs. Types are complete byte values, not bitmasks; 0x04 and up are reserved. Message boundaries delimit the payload (one message = one frame, always), and the protocol carries no compression headers — connect-content-encoding and connect-accept-encoding are unused. Compression is the WebSocket's own permessage-deflate extension instead, negotiated at the HTTP/1.1 upgrade via Sec-WebSocket-Extensions and applied transparently to every frame, headers and end-stream JSON included. The HTTP/2 bootstrap has no extension negotiation, so draft 2 travels uncompressed there. Served on /websocket-draft2.

Draft 3 Draft 2's framing + compression as a protocol option 
┌───────────┐┌────────────┐┌────────────────────┐
│ stream ID ││ descriptor ││ payload …          │
│ (4 bytes) ││ (C + type) ││ (rest of message)  │
└───────────┘└────────────┘└────────────────────┘
Descriptor Meaning
0x00 data — one RPC message
0x01 headers — opens every stream; JSON metadata with :path, content-type, …
0x02 end-stream — empty on requests (half-close); EndStreamResponse JSON on responses
0x03 reset — empty; aborts one stream
0x80 compressed bit (bit 7) — ORed onto any type: the payload is one raw DEFLATE stream

The descriptor byte is a bitfield: the frame type in bits 0–6 (values 0x04 and up reserved) plus the compressed flag in bit 7 — so 0x80 is compressed data and 0x81 compressed headers. Compression is negotiated once per connection through WebSocket subprotocols (Sec-WebSocket-Protocol): the client offers connect.bidi.d3.deflate and connect.bidi.d3, most preferred first; the server echoes its pick, and a handshake that settles on neither is refused. With the deflate token, either side may deflate any frame's payload (each frame is an independent RFC 1951 stream, no shared window) — senders skip payloads under 512 bytes and ones deflate can't shrink. connect-content-encoding / connect-accept-encoding are unused, and permessage-deflate is never accepted (it would compress twice). Because subprotocols travel on both bootstraps, draft 3 compresses identically over HTTP/1.1 and HTTP/2. Served on /websocket-draft3.

Draft 4 An ASCII frame head you can read on the wire 
7|1|{"metadata":{":path":["/connectrpc.eliza.v1.ElizaService/Converse"]}}
│ │ │
│ │ └─ payload — everything after the second "|", never escaped
│ └─── flags — 1 = headers  (0 data, 2 end-stream, 3 reset)
└───── stream ID — unpadded decimal ASCII, assigned by the client

7|0|{"sentence":"hello"}     one data frame, JSON codec
7|2|                         end-stream: the head, with no payload
Flags Meaning
0 data — one RPC message
1 headers — opens every stream; always JSON metadata with :path, content-type, …
2 end-stream — empty on requests (half-close); EndStreamResponse JSON on responses
3 reset — empty; aborts one stream

Both head fields are unpadded decimal ASCII, so a frame reads as text with no decoder ring — pick this transport above, open the Network tab, and watch the RPCs go by. Parsers split on the first two | bytes only, so a payload containing | needs no escaping. Frames whose payload is UTF‑8 are sent as text WebSocket messages, which is what makes devtools render them as text; with the default JSON codec that is every frame on the connection, and with protobuf only the data frames fall back to binary. The flags field is a bitfield: the frame type in the low 3 bits (types 4–7 reserved), five undefined flag bits above it. Receivers mask with & 7 and ignore unknown flags, so a later revision can OR one in — 7|8|… is a data frame carrying flag 8 — without a coordinated upgrade. Compression goes back to permessage-deflate as in draft 2 — a text head can't cheaply carry a compressed bit — which means draft 4 has no compression over the HTTP/2 bootstrap either. The head is variable width: 4 bytes at 7|1|, 6 once the stream counter passes 100, so its overhead grows with a connection's age rather than staying fixed at draft 2's 5. Served on /websocket-draft4.

The result: drafts 2 and 3 spend 5 bytes of protocol per message where draft 1 spends 9, and all three skip or shrink differently. Draft 1's gzip compresses everything, making small messages bigger and slower, but works end-to-end through any intermediary. Draft 2's permessage-deflate skips small messages and covers control payloads, but is best-effort (hop-dependent) and simply absent over HTTP/2 — and browsers never compress what they send with it. Draft 3 keeps draft 2's frame economy while making compression the protocol's own: it works on both bootstraps, in both directions, from every client. Draft 4 spends that hard-won frame economy back deliberately, buying a wire a human can read at the price of a head that grows as a connection ages. All four carry identical Connect semantics; see the benchmarks for what each choice costs and buys.

WebTransport needs almost none of this. QUIC already gives every RPC its own independently flow-controlled stream, with native half-close and cancellation, so there the protocol is exactly Connect envelopes (draft 1's, without the stream ID) plus the headers frame, and nothing else. The stream ID and reset frame exist only where the transport can't do that job itself.

Sharing one ordered TCP connection has a real cost, though: head-of-line blocking. A huge message on one stream, or a stalled consumer, delays every frame queued behind it, and unlike HTTP/2 there is no per-stream flow control. For RPCs that can't tolerate that, both clients take an option (connectionPerStream in TypeScript, WithConnectionPerStream() in Go) that dials a dedicated WebSocket connection per streaming RPC instead. It's purely a client-side choice: the protocol is identical either way, and a dedicated connection is just a multiplexed connection that happens to carry one stream.

Highlights worth noticing: draft 2 and 3 spend 5 bytes of protocol per message where draft 1 spends 9; draft 1's per-message gzip compresses everything, which makes small messages larger and slower; and draft 3 is the only variant where a JavaScript client compresses what it sends — permessage-deflate never compresses browser or Node uploads, while draft 3's protocol-level deflate shrinks the 16 KiB upload to a few hundred bytes.

Conclusions

What three coexisting drafts and a byte-counting benchmark suite settled. The full write-up lives in CONCLUSIONS.md.

Don't duplicate the layer below

A WebSocket message is already length-delimited, so an in-band payload length is pure redundancy: dropping it saved 4 bytes per frame and deleted an error class. The 9-byte→5-byte prefix shows up directly in the small-message numbers.

Where compression is negotiated matters most

Per-message metadata (draft 1) is end-to-end but threshold-less and unimplemented in JS clients. The WebSocket extension (draft 2) is an environment property: absent over HTTP/2, platform-dependent, and never applied to browser uploads. Protocol-negotiated (draft 3) is deterministic everywhere, in both directions, and configurable on either side.

Compressing everything is worse than nothing

Draft 1's threshold-less gzip makes tiny messages ~50% larger and doubles roundtrip latency. A size threshold plus “send raw if it didn't shrink” costs one bit and removes the pathology. The one thing per-frame compression can't match: permessage-deflate's shared window on long runs of tiny, similar messages.

Bootstraps expose hidden couplings

One wire protocol runs cleanly over both the HTTP/1.1 upgrade and HTTP/2 extended CONNECT — unless it depends on something optional below it, like draft 2's permessage-deflate, which simply doesn't exist on HTTP/2. And the h2 advertisement is origin-wide: every WebSocket endpoint must accept extended CONNECT before it can be enabled.

Fallback needs three contracts

Transports must distinguish establishment failures from RPC failures; every dial needs a timeout (the worst failure is a handshake that never settles); and retrying a streaming call needs a replayable view of the request iterable. All three were learned the hard way.

Recommendation

Draft 3 by default: draft 2's frame economy with compression that behaves identically everywhere. Draft 2 for maximum JS throughput on trusted HTTP/1.1 infrastructure or tiny-repetitive streams; draft 1 for pluggable algorithms or extension-stripping middleboxes; WebTransport when you control the UDP path; the Auto ladder when the environment is unknown.

Why is WebTransport not shown in the demo?

Because the server you are talking to right now can't speak it. The hosted version of this site runs on Cloudflare Workers, which don't yet support WebTransport: Workers expose no QUIC or UDP path to your code. Run the Go demo server locally and both transports work.

Both ends are fine on their own. Every major browser ships WebTransport now, and server-side support is mature in Go (quic-go/webtransport-go, which this project builds on), Rust (wtransport), and elsewhere.

What usually breaks is the path between them. WebTransport runs on HTTP/3 over QUIC, so UDP has to reach your handler and every hop has to pass Extended CONNECT. Load balancers and CDNs usually terminate HTTP/3 at the edge and talk HTTP/1.1 or HTTP/2 upstream, which the session can't cross. Serverless platforms tend not to offer UDP at all. Some networks drop UDP on port 443, where ordinary HTTP would fall back to TCP but WebTransport just fails.

Browsers also apply stricter certificate rules to WebTransport than to HTTPS. Firefox disables HTTP/3 when it sees a certificate chaining to a third-party root, which is common under corporate proxies and antivirus, and Chrome only accepts WebTransport certificates from well-known roots unless developer mode is on. A locally-installed CA like mkcert's trips both.

Hence the composite transport: unary RPCs stay on plain HTTP, streaming RPCs use WebTransport where the path allows it and WebSocket where it doesn't.
